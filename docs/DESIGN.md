# Binary Viewer — Design

Source requirement: [`requirements/2026-10-30_135401.md`](../requirements/2026-10-30_135401.md)

A fully client-side hex editor + binary format builder, hostable as static files (GitHub Pages).

## Decisions

Each decision has an [architecture decision record](decisions/README.md) with context, alternatives and consequences.

- [ADR-0001](decisions/0001-client-side-static-app.md): fully client-side static app, hosted on GitHub Pages (workflow publishing to `gh-pages`).
- [ADR-0002](decisions/0002-svelte-typescript-vite.md): UI in Svelte 5 + TypeScript, Vite; small runtime and fine-grained reactivity for a fast-updating grid/inspector.
- [ADR-0003](decisions/0003-own-declarative-format-language.md): own JSON format language with Kaitai Struct (KSY) semantics/naming and our own interpreter (the Kaitai JS runtime needs the whole file in memory and has no byte-range tracking; the compiler is GPL-3).
- [ADR-0004](decisions/0004-parsing-in-a-web-worker.md): parsing core is plain TS in a Web Worker, no WASM in v1 (interpreter over small slices; JS is fast enough).
- [ADR-0005](decisions/0005-lazy-byte-access-and-custom-hex-grid.md): byte access through `ByteSource` (Blob.slice paging + LRU), never the whole file; custom fixed-row-height DOM windowing for the hex grid (rows are uniform; no library needed).
- [ADR-0006](decisions/0006-editing-piece-table-and-save.md): editing as a piece table over the base source; save in place (File System Access) or by download.
- [ADR-0007](decisions/0007-untrusted-input-limits.md): files and specs are untrusted; limits and budgets in the engine.
- [ADR-0008](decisions/0008-spec-storage-indexeddb-and-folder-sync.md): specs in IndexedDB, optional local-folder sync, verify mode after timed-out writes.
- [ADR-0009](decisions/0009-no-network-requests.md): the app makes no network requests at runtime.
- [ADR-0010](decisions/0010-deferred-refs-and-navigation-links.md): deferred refs (`ref`/`expandRef`) and navigation links (`link`, `jumps`).
- [ADR-0011](decisions/0011-ide-shell-and-editor-tabs.md): IDE-style shell with editor tabs (file + spec), light/dark themes, bundled fonts.
- [ADR-0012](decisions/0012-preview-engine-worker.md): several spec tabs; spec previews on their own engine worker.

Two choices without an ADR:

- **Tests:** Vitest (unit), Playwright (E2E in `e2e/`: Chromium, plus Firefox for the path without the File System Access API). Every behaviour change ships with a test.
- **Browsers:** Chromium-first, graceful fallback, because the File System Access API is Chromium-only.

## Architecture

```
src/
  core/        framework-free, fully unit-tested
    byte-source.ts   ByteSource interface; BlobByteSource (Blob.slice + LRU page cache)
    edit-buffer.ts   piece table over a ByteSource (Phase 4); save.ts streams it to disk
    hex-format.ts    offset/byte/ASCII formatting helpers
    inspector/       Data Inspector decoders (Phase 2)
    engine/          format schema, expression parser, interpreter (Phase 3)
  worker/      Web Worker hosting parsing/detection/search (Phase 3)
  ui/          Svelte components (HexView, Inspector, StructureTree, Builder)
    shell/         window layout: TitleBar, ActivityBar, SideBar, EditorTabs, BottomPanel, Resizer, Welcome, CommandPalette; keys.ts (app-wide shortcuts)
    commands.ts    the command palette's registry (pure; built from App state and actions)
    formats/       FormatsState (shared library UI state), FormatList (side bar), FormatDetail (spec tab)
  formats/     built-in specs (bmp.json, zip.json)
```

### App shell (UI layout)

`App.svelte` wires the document and engine state to a window-sized grid; see [ADR-0011](decisions/0011-ide-shell-and-editor-tabs.md).

```
title bar:    brand (About), New, Open…, Save, Save As…, search field (palette), ?
activity bar | side bar (Structure | Formats) | tab bar: [file] [spec ×] [spec ●×]  | inspector
             |                               | editor header: breadcrumb, Go to      |
             |                               | editor body: hex grid | minimap      |
             |                               | Problems panel (file tab only)        |
status bar:   format, byte order, selection, insert/overwrite, parse summary, notices, size, zoom (not at 100%), theme (all buttons)
```

- **Editor tabs.** The tab bar holds the file tab (not closable) and one tab per open spec (name, modified dot, close button; it scrolls horizontally and keeps the active tab in view; arrows/Home/End move, Delete or middle-click closes). `activeTab` is `'file'` or `'spec'`; `FormatsState` holds the ordered `tabIds` and `activeSpecId`, and `specActive` (a spec tab is the shown one) replaces the old Viewer/Formats mode. Per-tab session state (draft, Builder/JSON/Docs view, save outcome, error) lives in the store, and a tab's modified state is derived from its draft and the saved text (`sameSpecText`), so it is right while the tab is not mounted. Only the active spec tab has mounted editors and a preview pane (keyed, so switching remounts them from the stored draft; the text, view and save status are kept; the JSON caret, selection, native undo and scroll, the Builder's undo history, the preview's enabled/collapsed state and tree expansion are not). The file and spec panels are both mounted; the hidden one is `visibility: hidden`, `inert` and `aria-hidden`. Choosing a spec in the side bar goes through `FormatsState.select` (activate the open tab, else open a new one after the active tab; never a prompt) and calls `onOpened`; closing a modified tab asks first and activates the right neighbour, else the left one, else the file tab. A rename on save (the id inside the JSON changed) moves the tab and its session; a delete or a spec removed by folder sync closes only its own tab. The page warns before unload while the file or any spec tab is modified.
- **Side bar.** Both views stay mounted (stacked, one hidden) so the structure tree keeps its scroll and expansion state. The Formats list marks specs that are open and specs with unsaved changes. The Structure tree stays live while a spec tab and its preview are showing, because previews run on their own worker (below).
- **Two engine workers** ([ADR-0012](decisions/0012-preview-engine-worker.md)). The viewer's `EngineClient` serves the open file (open, parse, expand, nodeAt, ranges, overview, setSpecs). Spec previews use a second client, created on the first preview and disposed when the last spec tab closes or the app is destroyed: before a preview parse it `open()`s the same document Blob as the viewer (`editor.toBlob(baseBlob)`, shared, not copied) unless it already has that exact state, then calls `parseDraft`; it never gets `setSpecs`. A preview result is dropped if a newer preview parse, a save or another document started (`previewToken`); the viewer's `engineToken` rules are separate. Saving blocks previews (the file being replaced is the one the worker reads). A failure of one worker does not affect the other.
- **Panels.** `Resizer` is a `role="separator"` with `aria-valuenow/min/max`; arrows move by 16 px, Home/End go to the limits, double-click resets. Side bar 200–600 px (default 300), inspector 240–520 (320), Problems 80 px up to 60% of the editor column (180). Sizes and open flags are stored under `binaryviewer.layout.*` (`src/ui/prefs.ts`) only when the user changes them, so a narrow screen's collapsed defaults (< 900 px: side bar and inspector start collapsed and open as drawers) are not frozen into storage.
- **Reset layout and the divider menu.** `App.resetLayout` clears the saved side bar, inspector and Problems sizes and the tree column widths, saves the three open flags as open and the minimap as shown, and sets the live state to what a first visit on this screen would show (the drawers stay closed on a narrow screen). It leaves the theme, the zoom, the side bar view and the recent commands. `Resizer` takes an optional `onResetLayout`; with it a right-click, `Shift+F10` or the Menu key opens a `role="menu"` with the single `role="menuitem"` "Reset layout" (a `position: fixed` box, the item focused; Escape or choosing it returns focus to the divider, a press elsewhere, a window resize, blur or any scroll just closes it; Tab closes it with focus back on the divider and its default prevented; the menu is moved back inside the viewport after it is measured; if Reset layout removes the divider, as when a panel closes on a narrow screen, focus goes to the editor region; the menu's own keys do not reach the divider's resize keys). A full menu component was not needed: one item, no submenus, no typeahead. The tree's column dividers are the same `Resizer` and take the same action.
- **Tree columns.** `StructureTree` gets `widths` (a `Partial<Record<TreeColumn, number | null>>`; px, or null / missing = the default width, with Name and Value flexible) and `onColumnWidth(column, px | null)`; `App` keeps them in `binaryviewer.layout.tree{Name,Value,Type,Offset,Size}Width` (`prefs.ts`: `TREE_COLUMNS`, minimums 80 / 60 / 40 / 50 / 36 px, at most 800; `resetLayout` clears all five). They become `--c-name`, `--c-value`, `--c-type`, `--c-offset` and `--c-size` on the tree (the grid columns of the header and every row; the row minimum width is the sum of the columns and is recomputed so the scroller scrolls sideways instead of squeezing). Size is the last data column and has a divider like the others: wider than the columns, the side bar just has empty space to the right of it (the 22 px badge cell stays fixed), which is simpler and more predictable than making the last column flexible, where a divider has nothing to move. In the narrow layout (container under 470 px) the Type column and its divider are hidden. Cells that no longer fit are cut with an ellipsis (`.row > span` is `overflow: hidden`) and carry their text as `title` (name, value, type, offset, size). The header's dividers are `Resizer`s in every column's cell (the column titles are `aria-hidden`; the separators are not), shown only when `onColumnWidth` is given, so the Formats preview tree has none. A value cell's `title` is `formatNodeValue(node, 512)` (the cell itself shows 200 characters); when it is longer than the cell, the treeitem also gets `aria-description` with it, since the accessible name only holds the 200 characters of the DOM text.
- **Zoom.** `uiScale` is one of 0.9, 1, 1.15, 1.3 (`prefs.ts`, `binaryviewer.uiScale`, removed at 1). `applyUiScale` sets CSS `zoom` and `--ui-scale` on `<html>`, so every size, dialogs included, scales together and nothing else is recomputed from font tokens. This works in Chromium and in Firefox 126 and later (the e2e tests run hex clicks, resizer drags and minimap clicks at 90%, 115% and 130% in both). What `zoom` does not do is rescale viewport units, so `100dvh`, `100vw` and the palette and About dialog limits divide by `--ui-scale`. Pointer coordinates (`clientX`, `getBoundingClientRect`) are in screen pixels while layout sizes are in the zoomed element's own pixels: `HexView` uses `elementFromPoint`, the minimap uses ratios, and `Resizer` divides drag distances by `visualScale()` (the root's `--ui-scale`, `src/ui/shell/zoom.ts`; measuring a 1 px divider's rect against its offset size rounds badly). The minimap canvas has one pixel per screen pixel (`devicePixelRatio` times `scale`). A viewport media query would still test the raw window, so every width breakpoint is a container query on `<body>` (`container: page / inline-size` in `app.css`; `@container page (max-width: ...)` in the status bar, Go to, minimap, start screen, About and palette; the title bar and the tree test their own width), whose width is in the zoomed CSS px. The one query that has to be a media query, the narrow layout switch in `App.svelte` (it decides whether the drawers exist), is rebuilt from the zoom: `900 * zoom - 1` screen px. `src/layout-queries.test.ts` fails on a new viewport width media query. `Ctrl+=`, `Ctrl++`, `Ctrl+-` and `Ctrl+0` come from `globalKey` (`zoom-in`, `zoom-out`, `zoom-reset`, numpad included); the page prevents them everywhere (also at the ends of the scale, and while the palette, About or a confirmation is open: the check runs before the dialogs' early return, so browser zoom never stacks on the page's).
- **Motion.** `--motion-in` 120 ms, `--motion-out` 80 ms, `--ease-out`, `--ease-in` in `app.css`; under `prefers-reduced-motion: reduce` the durations are 0 ms (`app.css.test.ts` parses it). Used with opacity and transform only: the palette open (fade and 4 px rise), the activity bar labels (fade and 4 px slide, after the 400 ms hover delay), the narrow-screen side bar drawer (a transition between its closed and open classes, so it also slides out), the inspector drawer (it is unmounted when closed, so it only slides in), the scrim, and the divider menu. The hex grid, the minimap and the tree rows never animate; collapsing a panel on a wide screen is instant because it changes the layout.
- **Hex banding.** `hexBanding` (default on, `binaryviewer.layout.hexBanding`, palette "Toggle hex row banding"). `HexView` adds `banded` to each row's `.hex` and `.ascii` columns; CSS draws a `linear-gradient` of the `--band` token over the second 8-byte group (from 22.7ch in the hex column, between byte 7 and byte 8, and from 8ch in the ASCII column), with the columns stretched to the row height so the bands join. The cells' own backgrounds (structure tints, node, selection) paint over it. Nothing is computed per byte.
- **Themes.** Tokens live in `src/app.css` (light base; dark under `prefers-color-scheme` unless `data-theme="light"`, or `data-theme="dark"`). The pref `binaryviewer.theme` is `light` or `dark`; absent means system. `index.html` applies it before first paint.
- **Breadcrumb bar.** `src/ui/shell/Breadcrumb.svelte` (labels, titles and the collapse rule are pure, in `breadcrumb.ts`) fills the editor header's left side: a `<nav aria-label="Structure path">` with an `<ol>` of buttons, "›" separators that are `aria-hidden`, and `aria-current="location"` on the last one. The segments are snapshots (`{id, name, typeName, offset, size, label, reveal}`), because lazy loads mutate the tree in place; they are rebuilt from the tree's own selection (`StructureTree`'s `onPath` gives the chain of rows from the root, which includes the elements of fixed-size lazy arrays), from a hex click (the worker's `nodeAt` path through `followPath`) and, after keyboard caret moves, from a `nodeAt` 150 ms after the last move (an own request counter drops late answers; a selection App itself made does not trigger it). A lazy array element shows as `name[index]`; selecting a segment calls `tree.reveal` with the path, `lazyIndex` and offset. A new parse, file or format None clears it; with a parse and nothing located only the root shows.
- **Region navigation.** `F6` / `Shift+F6` (`globalKey`) cycle the regions in visual order (`src/ui/shell/regions.ts`, pure ordering plus `firstFocusable`): activity bar, side bar, editor, Problems panel, inspector, status bar. Each container carries `data-region`; the current region is the nearest `data-region` ancestor of `document.activeElement`, and when focus is in none the editor is the target. Collapsed panels, closed narrow-screen drawers and the Problems panel in a spec tab are skipped. The palette's Focus commands open the region first.
- **Status bar.** The format name, parse summary, selection and edit mode are buttons that reuse existing actions (the palette opened straight into Choose format / Go to offset through its `initial` prop, `openAndFocus('bottom')`, `HexView.toggleInsert`); the format engine's and library's errors are an `role="alert"` item. The parse item's `role="status"` element always holds the full "Parsed: N nodes, E errors, W warnings" sentence (visually hidden once there is a summary); the compact button beside it is what is shown. Buttons are 24 px tall (the bar is 25 px with its top rule) and at least 24 px wide.
- **Colour groups.** One rule, in `src/core/groups.ts`, is used by the worker's `ranges` and `overview` (buckets and regions) and by the tree: the groups are the root's children, except that a root with exactly one child that has children is grouped by that child's children; group = index modulo 4. The tree marks a group node with an 8 px swatch and what is inside it with a 2 px rule in the same `--struct-n`. The minimap also paints a 1 px `--ground` line at the top of each region that touches the one before it, when both are at least 4 CSS px tall (`regionBoundaryRows`), so same-coloured neighbours stay apart. Region names (at most 64 characters) travel with `overview` for the minimap tooltip. The light theme's four colours are at least 3:1 on `--ground` and 1.4:1 apart in luminance from each other (dark too), and `--signal` is at least 3:1 on the ground and both chrome backgrounds; `src/app.css.test.ts` checks it.
- **Hit targets.** Controls are at least 24 x 24 CSS px (WCAG 2.5.8): tree rows are 24 px tall (the twisty fills the row; a jump button is 24 px tall with a 17 px pill drawn inside it), and panel buttons have `min-width`/`min-height` of 24 px. The divider (`Resizer`) keeps its 1 px line and has an invisible hit area 8 px to each side; hovering, dragging or focusing it draws a 2 px `--signal` line.
- **Fonts.** IBM Plex Sans Condensed (400/500/600) and IBM Plex Mono (400/500), latin subset, from `@fontsource` packages bundled by Vite (same-origin, no CDN).

### Command palette and global keys

`Ctrl+K` and `F1` (`Cmd+K` on macOS) open the palette, as does the title bar's search field (a button that looks like one, about 240 px wide and centred, an icon only below 720 px; the title bar stays the one place for app actions). `Ctrl+Shift+P` is not used: Firefox reserves it for a private window and a page cannot override it. Both keys reach the page and can be `preventDefault`-ed in Chromium and Firefox (the e2e tests record `defaultPrevented` from a window listener added after the app's own). F1 and Ctrl+K are not printable, so `HexView` does not touch them while editing (it handles Ctrl+Z/Y/C, Insert, Delete, Backspace and single-character keys only).

- **Global key handling.** One `keydown` handler on the window in `App.svelte`, in the bubbling phase, deciding via `globalKey(e)` (`src/ui/shell/keys.ts`, pure: palette, save, region navigation (F6 / Shift+F6), zoom in / out / reset (`Ctrl+=`, `Ctrl++`, `Ctrl+-`, `Ctrl+0`), or nothing; Alt and IME composition never match, and Shift only matters for F6 and the `+` and `_` zoom keys). It does nothing when `e.defaultPrevented` (a focused control already handled the key: `HexView`, `SpecJsonEditor` and `BuilderView` call `preventDefault` on Ctrl+Z/Y/S, so their keys never reach it), nor while the About dialog, a confirmation or the palette is open. Ctrl+S saves the file when the file tab is shown, under the same rules as the title bar's Save button (a file is open, no save running, not unreadable), and always keeps the browser's Save page dialog away; in a spec tab it is left to the spec editors. Escape still closes the narrow-screen drawers. The tree, the minimap and the resizers handle their own keys and do not call `preventDefault` on Ctrl+K or F1, so those open the palette from anywhere, including from text inputs.
- **Registry.** `src/ui/commands.ts` is pure: `buildCommands(ctx)` takes a `CommandContext` (getters over App state plus action callbacks) and returns `Command`s: id, label, group (File, Format, View, Tabs, Help), optional shortcut text, keywords, a hint ("Current"), a `disabledReason()` (null when the command can run) and either `run()` or `sub()`, which opens a sub-mode: an offset field (Go to offset: same parser and error texts as the editor header, `core/parse-offset.ts`) or a pick list (Choose format, Open format spec, Keyboard shortcuts, the last one read-only). Names that come from specs or files go through `sanitizeText`. The library's specs also appear as search-only "Open spec <name>" commands, which are not listed while the query is empty.
- **Matching.** `src/core/command-match.ts`: a case-insensitive subsequence match on code points, scored by dynamic programming (best alignment, not the first): +8 for a prefix, +6 for a word or camelCase start, +7 for a letter right after the previous match, small penalties for gaps and leading skips, a tiny preference for shorter labels. Whitespace in the query is ignored. At most 200 characters of a label and 100 of the query are matched. The result carries the matched ranges (UTF-16 indices); the palette renders them as `<span>`s from text bindings, never as markup. Commands found only through their keywords rank after label matches. Enter on a disabled best match does nothing (it never runs a lower-ranked command).
- **Palette UI.** `CommandPalette.svelte`: a modal at the top centre (560 px, viewport width minus 16 px gutters below 480 px), an ARIA combobox (`role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`) over a `role="listbox"` of `role="option"` rows in `role="group"`s (Recent, then the groups). Up/Down wrap, Home/End jump, PageUp/PageDown move by 8, Enter runs, Escape or a press on the backdrop closes, Backspace in an empty sub-mode goes back, Tab stays inside. The page behind is `inert`. Closing returns focus to the element that had it (the title bar button when opened from it) and only then runs the chosen command, so a command such as Go to offset can move focus on to the hex view. The last five commands used are kept in `binaryviewer.recentCommands` (local storage) and listed first while the query is empty. The open fade and 4 px rise use the motion tokens (120 ms, 0 ms under `prefers-reduced-motion: reduce`). A search or pick list shows at most 50 rows and says how many more matches there are; one persistent `role="status"` element announces the result count (only its text changes). A held Ctrl+K or F1 (`e.repeat`) is prevented but acts once, and Ctrl+S inside the palette is swallowed. Only commands that finished are remembered as recent (not abandoned sub-modes, search-only spec entries or tab switches). If the element that had focus is gone or inert after a command ran, focus goes to the active editor tab. In a spec tab the palette's Save reads "Save file" (it saves the binary file; Ctrl+S there saves the spec).

### Byte access (all phases)

- `ByteSource { size: number; read(offset, length): Promise<Uint8Array> }`.
- Reads are bounds-checked: negative, non-integer, or past-EOF requests are clamped or rejected — never trusted.
- `BlobByteSource` reads via `Blob.slice(...).arrayBuffer()` in fixed pages (default 64 KiB) with an LRU cache. The whole file is never loaded.
- Edits (Phase 4) are a piece table over the original source (see Editing below). Save streams original chunks + added pieces to `createWritable()` (Chromium) or a download (fallback).

### Structure minimap

A 64 px strip (`src/ui/Minimap.svelte`, hidden below 600 px viewport width, shown unless the `showMinimap` pref says otherwise; the palette's Hide/Show minimap commands set it) right of the hex grid that shows the whole file top to bottom. 64 px is wide enough for a 4 px viewport frame and band edges to read as shapes, and narrow enough not to cost the hex grid more than a few columns at the 900 px layout breakpoint.

- **Drawing.** One `<canvas>` sized to `devicePixelRatio` (a 4096-row strip is a handful of `fillRect`s per band, where SVG would mean thousands of nodes), repainted whenever the bands, viewport, selection, canvas size or theme change. Integer device-pixel rectangles only, no gradients or rounded corners: a covered run of rows is the group's `--struct-n-tint` with a 1 CSS px edge in `--struct-n` at its top and bottom; uncovered rows are `--ground` with a faint `--rule` hairline every 4 CSS px; the viewport is a `--signal` outline with a low-alpha fill (at least 4 px tall); the selection (or the tree-selected node) is a solid `--signal` bar at least 2 px tall. Colours are read from the computed CSS variables at paint time, so both themes work and a theme change repaints. Pure geometry (bucket to pixel rows, byte range to rows, pointer to offset) is in `src/core/minimap.ts`, the painter in `src/ui/minimap-paint.ts`.
- **Interaction.** A pointer press or drag centres the hex view on the offset under the pointer (`HexView.scrollToOffset(offset, true)`, which clamps at the ends); the wheel scrolls the grid by pixels (`scrollBy`). Nothing animates, so `prefers-reduced-motion` needs no special case. It is a `role="scrollbar"` (`aria-controls` the grid, `aria-valuenow` the top row's offset, `aria-valuemax` the last possible top offset, `aria-valuetext` "Offset 0x...") with PageUp/PageDown (one screen), Arrow keys (one row), Home and End. Hovering shows the offset under the pointer; no worker call is made while moving.
- **Data.** The strip asks the viewer worker for `overview(buckets)` with as many buckets as it has device pixels (re-asked after a resize, debounced 150 ms), after each successful parse and after every lazy page or ref load (the worker answers from its cache unless the tree really changed). Bands are drawn only while the overview's `size` equals the document size, so an edit that changes the length hides stale bands until the re-parse lands. With no format the strip stays a blank navigation aid (viewport frame and selection only). Bucket `b` covers bytes `[floor(b*size/N), floor((b+1)*size/N))`; its value is 0 (no parsed node touches it) or the dominant group + 1. The group is the index of the top-level group node modulo 4 (`src/core/groups.ts`: the root's children, or those of an only child), exactly as `ranges` assigns it, so the strip and the hex tints agree; dominance is by covered bytes (overlapping leaves count twice), a tie goes to the lower group, and one covered byte is enough to colour a bucket (a 14-byte header in a 64 MiB file is still a mark, but a bucket mostly covered by another group takes that group's colour). Leaves are the nodes without children, `bits` nodes skipped, so an unexpanded lazy array counts as covered by its own extent and a variable-size array that has loaded some elements covers only those (same as `ranges`). The worker computes it from its live tree in one pass over the leaves (`src/worker/overview.ts`): leaves covering whole buckets are added with a difference array, so the cost is O(nodes + buckets) and never depends on the file size (sub-millisecond for a 43,000-node ZIP; file sizes up to 2^53 are exact). It never reads file bytes. The bucket count is clamped to 16..4096 and to at most the file size (no empty buckets; a non-integer or negative count is an `error`, and so is a request while there is no parse result, so the strip keeps its last bands during a re-parse), the result is cached per (tree shape, bucket count, size) and dropped on open/parse and when `expand`/`expandRef` attach nodes, and the `Uint8Array` is transferred to the main thread. The response also lists `regions`: the same top-level group nodes as `{start, end, group, name}` (the node's name, at most 64 characters, for the strip's tooltip) in file order, at most 1024 (`truncated`), computed and cached with the buckets. Regions whose true height is under 2 CSS px (a 14-byte header in a 20 KB file) are drawn over the bands as 2 px lines in their colour (tint fill, full-colour edges), stacked in file order so neighbours do not hide each other and kept inside the strip (`smallRegionRows`). Fractional offsets from a hostile spec are normalised to whole bytes. The strip re-reads the device pixel ratio when the window moves between monitors, leaves Ctrl+wheel to the browser, and is focused by the browser on a click (no keyboard focus ring); it sits above the panel resizer's wider hit area so its bottom edge stays clickable.

### Hex view

- Fixed row height; visible rows = `floor(scrollTop / rowHeight)` + overscan. Only ~50–100 DOM rows exist.
- Browsers cap element height (~16–33M px); for files whose row count exceeds that, scroll position is mapped proportionally onto a capped spacer.
- 16 bytes/row; offsets in hex; ASCII column renders non-printables as `.`.
- Selection: click / shift-click / drag over bytes; anchor + caret model. A plain click selects exactly the clicked byte in the clicked column (the caret is on it, so typing edits it); the structure node that contains it is looked up (`onByteClick` -> `locate` -> `tree.reveal(..., keepSelection = true)`), selected in the tree and the breadcrumb and shown with the node highlight (`nodeRange`), without touching the hex selection (`onTreeSelect` gets `{ keepSelection: true }`). Selections made from the tree, the breadcrumb, a link or Problems still select the whole node range.
- Column header row: a sticky `.hrow` at the top of the scroller (`aria-hidden`: the data cells are plain spans, not gridcells, so column headers would head nothing and a screen reader would only read noise) with `Offset`, `00`-`0F` (`.hb`, the same width, margin and 8-byte gap as `.b`) and `0`-`F` (`.hc`, as `.c`); the labels of the caret's column get `here` (`--signal`, bold). The header is part of the scroller's height, so the row maths uses `viewportHeight = clientHeight - HEADER_HEIGHT (22)`: the window, `fullRows` (page sizes, scroll-into-view), the spacer and the minimap's `onViewport` all see only the data area, and the sticky row layer is placed at `top: 22px` below the header, so the first row is never covered. It follows `BYTES_PER_ROW` (16).
- Exports for the minimap: `scrollToOffset(offset, center)` and `scrollBy(px)`; `onViewport(start, end)` reports the bytes actually on screen (no overscan; `onViewChange` keeps reporting the rendered window used for tints).

### Format engine (Phase 3, extended in Phase 6a)

What the declarative engine (`src/core/engine/`) implements. Everything here is generic; nothing is format-specific. The user-facing language (field types and modifiers, expression grammar, validation limits, examples) is documented in [`SPEC-LANGUAGE.md`](SPEC-LANGUAGE.md); this section keeps the engine behaviour and internals.

- **Types and fields.** Field types, modifiers and the rules around them are in [`SPEC-LANGUAGE.md`](SPEC-LANGUAGE.md). Compatibility note: specs that combined `size` with `repeat` (the size would be ignored: wrap the sized element in its own type and repeat that), or named a field `lookup` (now a reserved word like `min`/`max`), no longer validate. The host byte order is never used.
- **Positioning.** Fields are sequential by default. `at` (absolute offset, inside the enclosing substream) and `find` (below) place a field without moving the parent cursor and are mutually exclusive; a failing sequential field stops the struct, placed fields still parse. Not implemented, and not planned: relative/pointer sugar (`rel`, `ptr`), `align`, TLV `chunks` and `scanBackFrom`. They are expressed with `at`, `find`, `switch` and `repeat`.
- **Guards.** `if` (boolean expression) and `ifMagic` (`{ at, bytes, mask? }`, at most 64 bytes): the field is skipped (reads as `null`) when the condition fails; both must pass and `if` is evaluated first. `ifMagic` is a quiet guard: a position that is negative, unsafe, `null`, outside the enclosing stream, or a short read (the bytes are not there) all mean "no". A real source I/O failure and an expression that cannot be evaluated are reported on the field like a bad `if`; a budget stop still ends the parse.
- **Signature search (`find`).** `{ bytes, mask?, from, window, direction, accept? }`. The window is `[from - window, from)` (`backward`) or `[from, from + window)` (`forward`), clipped to the enclosing stream; a signature must lie wholly inside it. The window is read in chunks of at most 64 KiB (overlapping by `bytes - 1`) through the normal read budget, so a hit near the end of a multi-GiB file costs about one window. Candidates are ordered nearest-to-`from` first. Without `accept` the nearest candidate wins. With `accept` (tiers of expressions, tried in order) each candidate is probe-parsed as the field's own type in a throw-away run (no nodes, no diagnostics, private node ids, at most `maxProbeSteps` steps and min(1 MiB, remaining budget) of reads / 1000 reads; its reads, bytes and steps are charged to the real run, and it spends the real run's `lookup` budget) and a tier is evaluated in that probe's scope (the probed type's fields, `_start`, `_io`, `_parent`); the first candidate a tier accepts wins, a failing or non-boolean expression rejects the candidate. No (accepted) candidate is a field error like a failed `at`. More than one hit adds a warning "N other matches in search window"; hitting `maxFindCandidates` is reported too. `find` cannot be combined with `at` or `repeat`.
- **Struct scope.** Every struct scope exposes `_start` (the absolute offset where the struct begins), also through member access (`eocd._start`). The other context names (`_io`, `_parent`, `_root`, `_index`, `_`) are listed in [`SPEC-LANGUAGE.md`](SPEC-LANGUAGE.md#names); `_parent` past the root reads as `null`.
- **Sized structs are self-delimiting.** A user-type field with a declared `size` always leaves the parent's cursor at `pos + size`: a failure inside it (truncated field, fatal `expect`, bad array element) is recorded on its own nodes and diagnostics but does not stop the parent struct or end the parent array (the field's own `assert`s are skipped, since the struct is only partly parsed). This is what keeps one malformed record of a length-prefixed list (TLV blocks) from hiding its siblings. Unsized structs still stop their parent when they fail. (Before Phase 6b a failure inside a sized struct also stopped the parent.)
- **Computed fields.** `{ "type": "value", "value": "<expr>" }` consumes no bytes, defines its name (integer, string, boolean, struct, `null`) and produces a size-0 node at the current cursor. An expression error is reported on that node and the value is `null`; it never fails the struct. `if`, `ifMagic`, `assert` and `ref` work on it; `size`, `repeat`, `at`, `find` and friends do not apply.
- **Expressions.** Hand-written parser (never `eval`), BigInt-safe, checked arithmetic, C-style conditional `c ? a : b` (short-circuit, lowest precedence), `&&`/`||`/`and`/`or`/`not`, `==` on `null`, `min`, `max` and `lookup(list, "member", value)`: the first element (a struct) of an array whose member equals the value, or `null`; the member must be a string literal. `lookup` only searches elements the interpreter kept (parsed eagerly, at most `eagerElements` per array); lazy and skimmed elements are not searched. All lookups of one parse (including `find` probes) or of one `expandLazy` / `expandRef` call together may examine `maxLookupScan` elements (the budget is per call, like the other per-call budgets, not cumulative across calls); the scan checks for abort every 1024 elements.
- **Deferred pointers (`ref`).** `{ type, at, doc? }` on any field: during parse `at` is evaluated (a safe offset no larger than the file size, else a warning and no ref) and the node records `ref: { typeName, offset }`; nothing is parsed. `expandRef(result, nodeId)` (worker request `expandRef`) parses the target type at that offset over the whole file, so it may leave the substream the ref was found in, with the owning struct's scope as `_parent` (so target expressions can read `_parent.some_field`), then attaches the subtree under the node (`ref.loaded`, target flagged `fromRef`) and returns it; opening twice (even concurrently) returns the same nodes. Per-call budgets (nodes, steps, I/O, lookup scan) are fresh per expansion, but all expansions of one parse result together may create at most `maxRefNodesTotal` nodes (1,000,000; a clear error when exhausted), refs inside an expanded target are only opened on demand, nothing is ever followed automatically. The structure tree shows "open <type> @ 0x..." under such a node. Retained refs are keyed by tree path, so reloading a lazy page replaces them instead of accumulating (`maxRefs` caps distinct refs; the nodes of a replaced page are no longer openable, which is fine because the UI replaces them on reload). `findNodeAt` prefers the primary tree where it really owns the byte: a hit that is the ref node or one of its ancestors (a container that merely encloses the target) loses to the expanded target, an unrelated sibling or leaf wins; the byte ranges include expanded targets.
- **Navigation links (`link`) and ref shortcuts (`jumps`).** Specs describe offsets and sizes (`off_bits`, `cd_offset`, `local_header_offset`, ...) whose targets the user wants to reach in one click, including data blocks that are never parsed into fields. `"link": { "at": "<expr>", "size"?: "<expr>", "label"?: "<string>" }` on a field parses nothing and reads nothing: while the field is parsed, `at` and `size` are evaluated in the field's scope (`_` is its value, earlier fields and `_root`/`_parent` are available, later fields are not yet) and the node gets `link: { offset, size, label? }`. A link is valid only if `at` is a safe non-negative integer inside the file (an offset at or past the end has nothing to select, so it gives no button); `size` is clamped to the end of the file, and an absent or `null` size means one byte (an explicit size of 0 is kept and only shows the position). A `null`, negative, over-2^53 or at-or-past-the-end result is a quiet "no link" (data in hostile files is routinely out of range); only an evaluation error (a non-integer, a failing expression) adds a warning on the node. Not allowed together with `repeat`. Because evaluation happens when the field is parsed, a link cannot use values computed later in the file: that is why the ZIP spec links the effective `cd_start`/`lho_eff` value fields (which include the stub correction `_root.delta`) and the raw EOCD `cd_offset` goes to the stored offset only (likewise the locator's `z64_eocd_offset`: the ZIP64 record position is computed later, so with a stub in front that raw link is off by the stub length). `"ref": { ..., "jumps": [{ "label", "path" }] }` (1-8 entries) adds shortcut buttons to a ref node: `path` is a dotted chain of field names inside the target type (`data`, `header.extra`), checked statically by the validator through user types (every segment must be a field of the current type; segments before the last must be single, non-repeated user-type fields, so switch-typed and array fields are rejected, only the last may be anything). The node records `ref.jumps` (a plain copy). Neither feature is followed automatically.
- **Strict expectations.** `expect` records a validation message and parsing continues; with `"fatal": true` a mismatch fails the field like a read error (see [`SPEC-LANGUAGE.md`](SPEC-LANGUAGE.md#expect-and-fatal)).
- Output: tree of `{ name, type, offset, size, value, children | lazy, ref }` that drives highlighting, jump-to and the structure tree. Large arrays are lazy: elements beyond `eagerElements` are parsed on demand (`expandLazy`).
- Untrusted-input limits (`DEFAULT_LIMITS`): recursion depth, node/skim/step budgets, total I/O bytes and read count, array counts bounded by the bytes that remain, (type, offset) cycle detection, forward-progress checks, `maxFindWindow` (1 MiB; the validator also rejects larger literal windows), `maxFindCandidates` (256 probes), `maxProbeSteps`, `maxLookupScan`, `maxRefs`; cancellable via `AbortSignal`. Specs themselves are untrusted too (size/depth caps, validator with JSON paths).
- Detection: magic bytes (incl. end-relative) outrank extension; ranked list, user override.
- Documentation is generated from the same schema (fields, magic, offsets, `find`/`ifMagic`/`value`/`ref`/`link`/`jumps`/`fatal`, `doc` strings; labels and paths are escaped like every other spec text).
- Structure tree navigation: selecting a node (click, keys, jump; not a hex click, see the Hex view) selects its inclusive byte range in the hex view (`selection` + the structure highlight), scrolls it into view when it is off screen and clamps to the file; only the rendered window is painted, so multi-megabyte nodes cost nothing. A node with `link` shows a compact "-> label" (or "-> 0xOFFSET") button in its value cell: it calls `onJump(offset, size)`, which App routes to the same select-and-reveal path as a node selection (size 0: no selection, the inspector and the view just go to the position). A node with `ref.jumps` shows one button per jump on its row: if the ref is not loaded it is opened through `loadRef` (the existing `expandRef` round trip, once even for repeated clicks, the every click takes a fresh token and only the newest click may select, whichever reference it is on and whether the open was started by a jump or by Enter / double-click on the "open" row; superseded requests are silent), then every ancestor of the node at `path` is expanded and that node is selected like a click on it. A path with no node (the field was skipped by `if`, e.g. `descriptor` without flag bit 3, or parsing stopped) selects the target and shows "... is not available: ... was not parsed". Buttons are real `<button>`s with aria-labels, Enter/Space on a focused button is left to the browser (arrow keys still navigate the tree), their clicks do not select or toggle the row, and after a click focus returns to the tree. In the Formats preview a link only sets the preview selection (then "Show in viewer"). Without an `onJump` handler no link buttons are drawn.

### ZIP (`src/formats/zip.json`)

The archive is read from the end: `eocd` is found by a bounded backward `find` (65557 bytes) with accept tiers (comment ends exactly at EOF, then fits in the file, then nearest). ZIP64 locator/record are found with `ifMagic`; effective entry count, directory size and offset are `value` fields that take the ZIP64 value only for the sentinel. `delta` (data in front of the archive) is the gap between where the directory should end and where its offset says, and 0 when the stored offsets are consistent (`stored_ok`). The central directory is `at`-placed and its entry array is itself `at`-placed, so only the first 1000 entries are parsed at open and the rest on demand (an array with sequential placement would be skimmed completely); the count is clamped to `size / 46`. Each entry carries a `ref` to its local header + data (`local_entry`, whose `_parent` is the central directory entry, so the data size comes from the directory). ZIP64 extra bodies read the header sentinels three `_parent` levels up. Nothing is decompressed, decrypted or CRC-checked.

Known ambiguities and limits:
- A fake EOCD inside the archive comment that is self-consistent at the very end of the file (its comment length reaches exactly the end) wins over the real one.
- A stub is not assumed when a central directory header sits at the stored offset AND the directory ends exactly at the EOCD / ZIP64 EOCD record (or at a digital signature record before it). That keeps signature records or a stub that is itself an archive from being misjudged; a stub that fakes both is taken as is. The ZIP64 record is found directly before the locator, at the stored offset, or by a 64 KiB backward scan from the locator that prefers a record ending exactly at the locator (so extensible data plus a stub work); a locator without any record is a `find` error on `z64_scan`.
- A data descriptor without signature whose CRC-32 equals 0x08074B50 is read as one with signature.
- Names are CP437 without flag bit 11 and UTF-8 with it; the archive comment (no flag) is shown as CP437. The Info-ZIP Unicode path is shown, not applied.
- Split (multi-disk) archives: warning, only the directory on the last disk; entries with a non-zero disk start have no reference. A count that wrapped at 65535 entries without ZIP64 shows only the declared number; exactly 65535 entries trigger the "ZIP64 values required" warning (0xFFFF is the sentinel).
- The "bytes precede the archive" warning cannot print the byte count (assert messages are static); it is the `delta` node.
- Data descriptor sizes are 8 bytes when the local header has a ZIP64 block or the central directory marks the entry ZIP64 (sentinel or a size of 4 GiB or more); a local ZIP64 block is read as far as it goes (zeroed 16-byte blocks of streaming writers included).
- Per entry the tree is about 60 nodes (flag/time/attribute bit fields included): with 1000 eager entries this stays under the 100k node limit unless entries carry very many extra blocks.
- ZIP navigation: `cd_entry.local_header` has jumps "local header" / "data" / "descriptor" (-> `local_entry.header` / `data` / `descriptor`; `data` is the entry's compressed data, `comp_size_eff` bytes). `lho_eff` and `local_header_offset` (and the ZIP64 extra field's) link to the 30 fixed header bytes (the real header length is only known in the local header itself); `cd_start` and the EOCD / ZIP64 `cd_offset` link to the central directory (`cd_size_eff` / `cd_size` bytes; the raw ones ignore a stub: use `cd_start` then), the locator's `z64_eocd_offset` to the 56-byte ZIP64 record. Sentinel values (0xFFFFFFFF) give no raw link; the effective fields carry the real target.
- BMP navigation: `file_header.off_bits` links to the pixel data (to the end of the file, because the pixel size is only known after the DIB header; the `pixels` field is the exact array); V5 `profile_data` / `profile_size` link to the embedded or linked profile at the absolute position `14 + profile_data`.
- Opened refs inside lazily loaded variable-size pages (all central directory entries) are visible to `nodeAt`/`ranges` (the worker rebuilds its index after `expand` and `expandRef`); fixed-size lazy pages are still detached copies, which no built-in spec uses.
- Format `extensions` may now list up to 64 entries (was 32).

### Editing (Phase 4)

- `EditBuffer` (src/core/edit-buffer.ts) is a piece table over the base `ByteSource`: `orig` pieces point into the base, `added` pieces into an append-only chunked store (cap 256 MiB; history cap 10k steps). Piece lookup is a binary search over cached offsets; an edit costs O(pieces after the edit), fine to ~100k pieces. Adjacent contiguous pieces are merged.
- Keyboard: hex digits edit nibbles (first = high, second = low, then advance); the ASCII column writes printable ASCII; Insert toggles Overwrite/Insert (shown in the status bar). **Delete always deletes** (selection, or the byte at the caret) in both modes, and Backspace deletes the selection or the byte before the caret; this has not been checked against HxD. Pastes go to the start of the selection and do not replace the rest of it. Copy is hex text only.
- Undo steps: typed edits at adjacent positions within 1 s coalesce; arrows, clicks and go-to break the group. Saving clears the history (the base is replaced).
- After edits the worker is re-opened (debounced 300 ms) on `editBuffer.toBlob(baseBlob)` (lazy slices, no copy) and the chosen spec is parsed again; the tree keeps expansion/selection for nodes whose name path still matches.
- Save (src/core/save.ts): `streamPieces` yields Blob slices / byte chunks (4 MiB max). In-place via a `FileSystemFileHandle` (`createWritable()` without `keepExistingData`; aborted on any error; after `close()` the buffer is rebased onto `handle.getFile()` at once because the old File becomes unreadable). Without a handle: Save As via `showSaveFilePicker`; without the API: a download.
- Save safety: Save first awaits the HexView edit queue (`settled()`), then locks editing, cancels the pending re-parse and blocks New/Open/drop until it ends; queued edits that run after the lock are dropped. If the re-read after `close()` fails, the data is on disk but the document is frozen read-only with a notice (reopen the file); if the new file's size differs from what was written, the file is reloaded from disk with a notice. Download saves rebase onto a lazy Blob of the saved content (releasing the added store) and count as saved once the download starts: the browser reports no completion, so cancelling the download in the browser leaves the document marked clean. `toBlob` caches one Blob per added-store chunk. After a download save the typed bytes live in the browser's Blob storage (the rebase base is a lazy Blob of the saved content, which references them), so memory is not freed, but the 256 MiB added-store cap applies per save cycle.

## Known risks

- Two I/O code paths (Chromium vs fallback) to build and test.
- Saving a huge file is a full rewrite.
- Download-based save in fallback browsers may not be memory-bounded.
- **Folder sync and timed-out writes.** A file-system call that does not answer within 30 s is abandoned, but the browser may still complete it later (a stale write can land at any time). After any folder *timeout* the library therefore stops trusting everything it remembers about the folder: the folder is marked "needs permission", the remembered per-file state (`known`) is cleared, and a persisted flag `folderNeedsVerify` is set. Until the user reconnects, saves stay local (message "Folder needs verification after a timed-out write"). The first sync after reconnecting runs in *verify mode*: it writes nothing and deletes nothing, keeps pending deletes, keeps every local spec as is, saves each *differing* folder file as a local conflict copy `<id>-conflict-<n>` (identical copies are reused, never duplicated), records equal files as known, and adds files that have no local spec. Afterwards the flag is cleared and later syncs are normal (so a local version that differs from the folder may then be pushed, with the folder's version safe in the copy). Residual risk, accepted: a timed-out write that lands *after* the verify sync. Writes realistically land within seconds, and the verify sync only runs once the user reconnects, so no further machinery is built for that window. Deleting a spec while verification is pending, or whose file has no remembered content, never deletes the file: the user is told to delete it manually.
- **Verify mode keeps the local spec.** The verify sync never decides in favour of the folder: if a file differs, the local spec stays the spec and the folder's version is saved as a conflict copy. A legitimate external edit made during the timeout window therefore ends up as the conflict copy, and the next normal sync pushes the local version over the folder file. Conflict copies are ordinary specs and are not pinned: editing or deleting a copy before that next sync is a user action and can discard that version. Verification only completes when the whole folder was read and every differing file was kept as a copy; otherwise the flag stays set (a folder with more than 500 `.json` files can never be verified: saves stay local and a persistent message says so). Connecting or disconnecting a folder clears the flag, which is the escape hatch. A spec deleted while verification is pending leaves a tombstone (a pending delete without content hash): the file is never deleted, a sync will not bring the spec back, the user is told to remove the file manually, and creating or importing the id again clears the tombstone.
